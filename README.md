# LDA Inventory

Flutter foundation for the LDA inventory application. Firebase startup configuration is present, but inventory business logic has not been implemented.

## Supported targets

The project is scaffolded for Android, iOS, and web only.

## Local checks

Use the pinned local Flutter SDK from the repository root:

```sh
FLUTTER_SUPPRESS_ANALYTICS=true $HOME/develop/flutter/bin/flutter analyze
FLUTTER_SUPPRESS_ANALYTICS=true $HOME/develop/flutter/bin/flutter test
```

Run the app on an available device with:

```sh
FLUTTER_SUPPRESS_ANALYTICS=true $HOME/develop/flutter/bin/flutter run
```

## Development Firebase configuration

Android and web client configuration for the development project
`lda-inventory-dev-mx` is generated by FlutterFire CLI. The generated files are
`lib/firebase_options.dart` and `android/app/google-services.json`; do not edit
them manually. The iOS app is registered and its plist was downloaded, but
FlutterFire could not finish Xcode project integration because the local Ruby
`xcodeproj` tooling is unavailable.

Regenerate configuration after installing the missing iOS tooling with:

```sh
PATH="$HOME/develop/flutter/bin:$HOME/.local/share/lda-firebase-tools/node_modules/.bin:$HOME/.pub-cache/bin:$PATH" \
  $HOME/.pub-cache/bin/flutterfire configure \
  --project=lda-inventory-dev-mx \
  --platforms=android,ios,web \
  --android-package-name=com.ldasoftware.lda_inventory \
  --ios-bundle-id=com.ldasoftware.ldaInventory \
  --out=lib/firebase_options.dart \
  --yes --overwrite-firebase-options
```

This client configuration contains public Firebase identifiers only. It does
not include service-account credentials or private keys, and it does not enable
billing, Cloud Storage, or Cloud Functions.

## Local Firebase boundary

The emulator configuration continues to use the explicit demo project ID
`demo-lda-inventory`. The `.firebaserc` `dev` alias targets the development
project, so local emulator commands must continue passing
`--project demo-lda-inventory` explicitly. There is no production project,
Functions emulator, or Hosting emulator in this slice. Only Auth, Firestore,
and Storage emulators are configured locally.

Install the pinned rules-test dependencies and run the local security suite:

```sh
npm --prefix firebase/tests ci
$HOME/.local/share/lda-firebase-tools/node_modules/.bin/firebase \
  emulators:exec --project demo-lda-inventory \
  --only auth,firestore,storage \
  'npm --prefix firebase run test:rules'
```

The minimal local data contract is:

- `products/{productId}`: authenticated catalog reads; no acquisition cost.
- `branches/{branchId}/stock/{productId}`: administrator reads or seller reads
  when the `branchId` custom claim matches the path.
- `costs/{productId}`: administrator-only acquisition-cost reads.
- `inventoryMovements/{movementId}`: administrator reads or branch-matched
  seller reads based on the document `branchId`; client writes are denied.
- Storage `branches/{branchId}/products/{productId}/{fileName}`: administrator
  reads or branch-matched seller reads.

The local tests simulate trusted custom claims with roles `administrator` and
`seller`. Every direct Firestore inventory mutation and every direct Storage
mutation is denied, including for administrators. Future trusted server code
must perform those writes with validation and auditing; no such business logic
is part of this local-boundary slice.

Firestore rules cannot hide selected fields inside a readable document.
Therefore `products/{productId}` documents **MUST exclude acquisition costs**,
and cost data must remain physically separate under `costs/{productId}`.
Physically separated costs and server-owned inventory writes are mandatory
schema constraints for the next implementation phase, not field filtering that
these rules can provide.

## Production mode

Build with `--dart-define=LDA_FIREBASE_PRODUCTION=true` to sign in against the
real Firebase project `lda-inventory-dev-mx` (the options in
`lib/firebase_options.dart`). It uses the same gateways and the same
`role`/`branchId` custom claims as the emulator mode, never connects to the
emulators, and shows connection copy without emulator wording. Combining it
with `LDA_LOCAL_EMULATORS=true` is ambiguous, so the app stays offline.

Writes go through Cloud Functions, which are not deployed yet (the project is
on the Spark plan), so until they are only sign-in and reads can work. Every
callable already accepts exactly two runtimes: the `demo-lda-inventory`
emulator and a deployed `lda-inventory-dev-mx` runtime with no emulator
variables (`functions/src/runtime-project.js`); any other project is refused.
Callable CORS stays localhost-only until a production web origin is chosen;
the Android and iOS apps are not subject to CORS.

### Preparing the real project

Real accounts are created by a person in the Firebase console (email and
password); `functions/scripts/provision-production.mjs` then creates the
branches and gives each listed account its `role`/`branchId` claims. Start
from `functions/scripts/production-plan.example.json`:

```sh
cd functions
# Validate only (default): reads the plan, touches nothing.
npm run provision:production -- --project lda-inventory-dev-mx --plan my-plan.json
# Write, with Application Default Credentials for the project.
npm run provision:production -- --project lda-inventory-dev-mx --plan my-plan.json --apply
```

Every check runs before the first write. A missing account, a branch whose
stored name or code differs, a branch code already used by another branch,
an account that already has a different role or branch, or one with other
custom claims (which `setCustomUserClaims` would erase) refuses the whole
apply with nothing written. Emails are compared case-insensitively, as
Firebase Auth does. Re-running the same plan is a no-op. Any other
project, and `--apply` while a Firebase emulator variable is set, are
refused.

## Running against the local emulators

Start the demo emulators first, then build with
`--dart-define=LDA_LOCAL_EMULATORS=true`:

- **Android emulator**: no extra setup. The app reaches the host through the
  emulator alias `10.0.2.2`.
- **iOS simulator**: no extra setup. The simulator shares the host loopback
  `127.0.0.1`.
- **Physical Android device over USB**: forward the emulator ports to the
  device, then add `--dart-define=LDA_ANDROID_USB_REVERSE=true` so the app
  uses the device loopback `127.0.0.1` instead of `10.0.2.2`:

  ```sh
  for port in 9099 8080 5001; do adb reverse tcp:$port tcp:$port; done
  flutter run -d <device-id> \
    --dart-define=LDA_LOCAL_EMULATORS=true \
    --dart-define=LDA_ANDROID_USB_REVERSE=true
  ```

- **Physical iPhone over Wi-Fi** (partial): an iPhone cannot reach the Mac's
  loopback, so pass the Mac's private LAN address with
  `--dart-define=LDA_IOS_EMULATOR_HOST=<192.168.x.y>`. Only 10/8, 172.16/12
  and 192.168/16 addresses are accepted. The emulators must accept
  connections on that address. Sign-in and the live catalog work this way.
  **Functions callables do not**: the native iOS Functions SDK refuses to send
  the Auth token over HTTP to a non-loopback host (`unauthenticated`).

Plain HTTP to the emulators is allowed only in debug builds and only for
`10.0.2.2` and `127.0.0.1`
(`android/app/src/debug/res/xml/network_security_config.xml`).

## Native smoke test

`integration_test/native_smoke_test.dart` signs in as the demo seller, waits
for the live catalog and opens Correcciones, proving that a real Android or
iOS runtime reaches Auth, Firestore and Functions. It only reads data. With
the demo emulators running and seeded, pass the same defines as the route you
are testing:

```sh
# iOS simulator or Android emulator
flutter test integration_test/native_smoke_test.dart -d <device-id> \
  --dart-define=LDA_LOCAL_EMULATORS=true

# Physical Android device over USB (after the adb reverse loop above)
flutter test integration_test/native_smoke_test.dart -d <device-id> \
  --dart-define=LDA_LOCAL_EMULATORS=true \
  --dart-define=LDA_ANDROID_USB_REVERSE=true
```

Without `LDA_LOCAL_EMULATORS=true` the test is skipped. Plain `flutter test`
runs only `test/` and never this file.

## Camera scan on a device

`integration_test/qr_scan_device_test.dart` checks the product QR scanner on
real hardware: it opens the sheet, waits for one of the real camera outcomes
(ready, permission denied, or no camera), and closes it again. It never uses
the emulators, and plain `flutter test` does not run it.

`flutter test` builds, installs, runs and then uninstalls the app, so grant the
camera permission first; otherwise the sheet shows the denied state on purpose:

```sh
adb shell pm grant com.ldasoftware.lda_inventory android.permission.CAMERA
flutter test integration_test/qr_scan_device_test.dart -d <device-id>
```

The second test decodes a code that a person has to aim at, so it is opt-in:

```sh
flutter test integration_test/qr_scan_device_test.dart -d <device-id> \
  --dart-define=LDA_CAMERA_DETECTION=true
```

Show a product QR on another screen while it runs: it waits up to 60 seconds
and passes only when the decoded payload is the code the search matches
(`PRD-COFFEE-001` in the fixture).

Validated 2026-10-20 on a physical Huawei HBP-LX9 (Android 12): both tests
green.
